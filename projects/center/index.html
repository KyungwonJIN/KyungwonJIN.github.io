배경

세션이 열 개를 넘으면 생기는 일

에이전트 하나는 터미널 하나로 충분했지만, 업무 · 실험 · 측정을 나눠 동시에 돌리자 사람이 병목이 됐습니다.

01 — 무엇이 불편했나

  • 누가 기다리는지 모름 — 어느 세션이 권한 승인이나 선택을 기다리는지 일일이 창을 돌며 확인해야 했습니다.
  • 무엇을 하는지 모름 — 세션마다 지금 하는 일과 언제 멈췄는지를 알기 어려웠습니다.
  • 다시 열기가 번거로움 — 창을 닫거나 재부팅하면 세션 ID를 찾아 붙여 다시 열어야 했습니다.
작업

기능 → 설계 결정 → 개선 이력

02 — 주요 기능

  • 세션 보드 — 카테고리별 픽셀 캐릭터가 상태(작업 중 · 대기 · 입력 필요 · 꺼짐)를 표정으로 보여 줍니다. 여러 개를 골라 한꺼번에 지시 · 이동 · 종료합니다.
  • 처리함 — 터미널 화면에서 권한 · 선택 · 폴더 신뢰 · 턴 끝 질문을 감지해 버튼으로 답하게 하고, 데스크톱 알림을 띄웁니다.
  • 총괄 세션 · 지시함 — 총괄 에이전트가 사용자 지시를 담당 세션에 전달하고, 연결이 끊기면 경고합니다.
  • 세션 간 협업 API — 의견만 구하는 검토와 일을 맡기는 위임을 나누고, 공용 자원은 주인 세션 하나만 바꿀 수 있게 했습니다.
  • 지식 증류 · 주입 — 세션을 닫기 전에 인수인계 카드로 증류하고, 새 세션을 열 때 골라 넣습니다.
  • 운영 — 재부팅 후 세션 복구, 자동 재기동 감시, GPU 잡(Slurm) 배지, 메모리 막대와 정리 추천, 사용량 대시보드, 원격 서버(ssh) 세션.
  • 배포 — Windows 원클릭 설치기(11단계, 업데이트 모드). 배포판을 빌드할 때 개인정보 · 내부 주소 금지어를 검사합니다.

03 — 설계 결정 3가지

① 위험한 동작은 사람이 누른 응답만 승인으로 인정

결정

삭제 · 배포 · 재시작이 필요하면 세션이 승인 카드를 올리고, 사람이 보드에서 직접 누른 응답만 승인으로 받습니다. 스크립트나 다른 세션이 대신 누른 응답은 승인으로 치지 않습니다.

이유

에이전트가 여러 개일수록 "누군가 허락했겠지"라는 착각이 생기기 쉽습니다. 승인 출처를 기록에 남겨 구분했습니다.

② 바깥에서 들어온 글은 사람이 확인한 뒤에만 규칙으로

결정

웹에서 가져온 내용으로 만든 규칙 카드는 사람이 승인해야 다른 세션에 주입됩니다.

이유

증류 · 주입 경로가 그대로 프롬프트 주입 경로가 될 수 있어서입니다.

③ 서로 기다리다 멈추지 않게

결정

A가 B에게 묻는 동안 B가 A에게 보낸 요청이 남아 있으면 새 요청을 즉시 돌려보내고, 알림만 필요한 요청은 답을 기다리지 않게 했습니다.

이유

세션끼리 서로의 답을 기다리면 둘 다 시간 초과로 끝나는 교착이 실제로 생겼습니다.
