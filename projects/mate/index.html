배경

모델 코드 바깥에서 쓰는 시간

ML 실무의 상당 부분은 모델 코드가 아니라 그 주변에서 소모됩니다. 흩어진 주변 작업을 하나의 루프로 잇는 도구가 필요했습니다.

01 — 왜 만들었나

문제는 모델 코드 자체보다 그 주변이었습니다. 같은 종류의 작업이 반복되는데, 그 흔적은 매번 스크립트와 터미널, 노트북과 스프레드시트로 흩어졌습니다.

  • 라벨링 · 검수 — 대상을 매번 스크립트로 잘라내고, 결과는 손으로 취합했습니다.
  • 학습 — 어디에 어떤 설정으로 던졌는지가 터미널 히스토리에만 남았습니다.
  • 평가 — 결과가 노트북과 스프레드시트에 흩어졌습니다.

이 과정을 브라우저 도구 하나로 묶기로 하고, 실무에 쓰려고 직접 설계·개발했습니다.

02 — 초점 — 데이터 엔진 루프

기능 목록은 길지만 초점은 한 문장입니다 — 모델이 기존 라벨과 다르게 본 곳만 사람이 본다. 전체를 처음부터 다시 훑는 대신, 아래 루프를 한 도구 안에서 닫는 것을 목표로 설계했습니다.

  • 오토라벨 — YOLO 프리라벨, SAM 클릭·텍스트 분할, OpenAI 호환으로 서빙한 VLM의 검출·검증·태깅
  • 불일치 검사 — 기존 라벨과 모델 예측을 비교합니다. 검사는 판정만 기록하고 라벨은 바꾸지 않습니다.
  • 우선순위 검수 — 우선순위 점수를 매기고, 키보드 집중 검수 큐에서 승인·반려합니다.
  • 데이터셋 버전 — 검수 결과를 분할과 매니페스트 sha256으로 고정한 불변 버전으로 만듭니다.
  • 재학습 — Slurm으로 학습을 제출하고, 학습한 모델을 다시 보조 도구로 연결합니다.

실제로 수만 장 규모 객체 검출 데이터의 기존 라벨을 전수 검수할 때 이 루프를 썼습니다. 승인된 수백 장으로 VLM을 LoRA 튜닝하고 가벼운 크롭 분류기를 학습한 뒤, 라벨과 모델이 다르게 본 이미지만 사람이 검수했습니다.

작업

설계 → 실사용 → 다음 단계

03 — 설계 결정 3가지

① 레포 하나 · 앱 하나, 경계는 플러그인 계약으로

결정

파이썬 패키지 하나에 API 서버(FastAPI)와 React 프런트를 함께 번들했습니다. 기능 모듈(label · train 등)은 서로 직접 import하지 않고 core만 거칩니다. Trainer · Exporter · Synthesizer · Assist · Embedder는 레지스트리에 등록하는 플러그인으로 분리했습니다.

이유

1인 개발로 기능이 빠르게 늘어나도 모듈 사이의 경계가 무너지지 않게 하려는 것입니다.

② 라벨은 append-only 스냅샷, 데이터셋 버전은 불변

결정

라벨은 덮어쓰지 않고 append-only 스냅샷으로 쌓고, 데이터셋 버전은 분할과 매니페스트 sha256으로 고정한 불변 버전으로 만듭니다. 모델 검사는 판정만 기록할 뿐 라벨을 바꾸지 않습니다. 편집기는 base_version을 기준으로 저장해, 그 사이 라벨이 바뀌었으면 오래된 저장을 409로 거절합니다.

이유

이미 완성된 데이터셋 위에서도 검사를 안전하게 반복할 수 있고, 학습 결과를 그 학습에 쓰인 정확한 데이터에 연결할 수 있습니다.

③ 폐쇄망 전제, 모든 작업은 Run으로 기록

결정

외부에서 아무것도 내려받지 않고, 호스트 · 경로 · 스케줄러 같은 환경 값은 설정 파일에만 둡니다. 오토라벨 · 검사 · 임베딩 · 버전 생성 · 학습(Slurm 제출) · 서빙은 모두 단계 · 진행률 · 취소 · 산출물을 가진 Run으로 남습니다.

이유

인터넷이 없는 클러스터에서 재현성과 계보를 확보하기 위해서입니다. 학습 제출도 터미널 히스토리가 아니라 Run 기록으로 남습니다.

04 — 사람 손을 최소화하는 오토라벨 사이클 2026.09 ~ 10

사람이 손대는 곳을 클래스 정의 · 예외 확인 · 표본 검수 세 군데로 줄이고, 나머지는 한 바퀴가 스스로 돌게 했습니다.

  • 일괄 오토라벨 → 합의 판정 — 검출기 · 크롭 분류기 · VLM 등 여러 엔진의 판정을 맞춰 봅니다. 기준을 겨우 넘은 매칭은 합의로 치지 않고 예외로 보냅니다.
  • 자동 확정 · 예외 큐 — 합의한 장은 자동 승인(사람의 승인과 구별해 기록), 의견이 갈린 장은 불일치 검수 큐로 갑니다.
  • 층화 표본 검사 — 클래스 조합 · 크기 층마다 표본을 뽑아 사람이 봅니다. 표본 정확도가 합격선(97%)에 못 미치면 자동 확정을 되돌리고, 미달인 층만 따로 되돌리기도 합니다.
  • 버전 → 재학습 → 검출기 교체 — 사람이 승인한 장만으로 버전을 만들어 재학습하고, 그 가중치를 다음 오토라벨의 검출기로 겁니다. 엔진끼리 합의한 라벨로 엔진을 다시 가르치면 버릇이 굳어서 뺐습니다.
문제

전수 검사가 느려 한 바퀴를 돌리기 어려웠고, 상세 화면도 열 때마다 기다려야 했습니다.

결과

크롭 분류기 검사 526 → 14 ms/장(약 6만 장 15분), 상세 화면 2.2 → 0.48초. 무인 1바퀴 합의율은 약 85%로, 쉬운 85%는 무인 확정하고 어려운 장만 사람이 보는 기준을 세웠습니다. 표본이 합격선에 못 미칠 때 자동 확정이 되돌아가는 안전장치도 실제로 동작하는 것을 확인했습니다.

05 — 실사용에서 고친 것

객체 검출 데이터 검수 외에 소규모 키포인트 · 영상 프레임 데이터 라벨링에도 쓰고 있습니다. 실사용에서 드러난 문제와 고친 방법입니다.

문제

이미지를 전환하는 도중 이전 이미지의 저장 응답이 늦게 도착하면, 그 응답이 다음 이미지의 라벨을 덮어쓰는 오염이 생겼습니다.

접근

편집 상태를 문서(이미지) 단위로 관리하도록 바꾸고, 서버 쪽에 버전 가드를 두어 기준 버전이 맞지 않는 저장을 받지 않게 했습니다.

결과

늦게 도착한 저장 응답이 다른 이미지의 라벨을 덮어쓰는 경로를 차단했습니다.
